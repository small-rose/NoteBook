## 1. API 治理：从「一个项目」到「一个平台」

当 API 数量从 10 个涨到 1000 个，真正的问题不再是「怎么写 Controller」，而是：

- 不同团队的接口风格五花八门，前端苦不堪言。
- 接口上线后没人知道谁在用、能不能下线。
- 文档、代码、网关配置三张皮，改一处忘两处。

**API 治理（API Governance）**就是用「规范 + 工具 + 流程」解决这些问题。

### 1.1 治理三板斧

| 层级 | 手段 | 示例 |
|------|------|------|
| 规范 | 制定并强制执行 API 风格指南 | 公司级《RESTful API 设计规范》，统一命名/状态码/分页/错误体 |
| 工具 | 规范落进工具链，自动卡点 | CI 里跑 Spectral（OpenAPI 规则检查）、契约测试、自动化文档 |
| 流程 | API 全生命周期管理 | 设计评审 → 开发 → 测试 → 发布 → 监控 → 下线，每个接口有 Owner 和生命周期状态 |

### 1.2 契约先行（Design-First / Contract-First）

传统流程：先写代码 → 再补文档 → 前后端联调对不上。

契约先行：**先定 OpenAPI 契约（.yaml）→ 评审 → 前后端各自照契约并行开发 → 用契约做自动化测试**。

```
OpenAPI 契约（唯一真相源 Single Source of Truth）
        │
        ├──→ 后端：契约生成接口骨架（Codegen）
        ├──→ 前端：契约生成 TS 类型 + Mock（MSW / Swagger-Mock）
        ├──→ 测试：契约测试（Pact / Schemathesis）
        └──→ 文档：契约渲染出开发者门户
```

好处：联调返工大幅减少；接口变更在「改契约」这一步就暴露，而不是等联调。

### 1.3 开发者门户

把全公司 API 汇聚成门户（如基于 swagger-ui / Apifox / Redoc / 自研），提供：
- 搜索与在线调试（Try it out）
- 各语言 SDK 下载
- 配额、Key 申请、调用统计

## 2. 微服务下的 RESTful 与 API 网关

微服务架构下，对外暴露的不是一堆后端服务的 IP，而是统一的 **API 网关（API Gateway）**。

```
客户端 ──→ API 网关 ──┬──→ 用户服务   /users
                      ├──→ 订单服务   /orders
                      └──→ 图书服务   /books
```

### 2.1 网关职责

| 职责 | 说明 |
|------|------|
| 统一入口 | 对外一个域名，内部按路径路由到不同服务 |
| 鉴权 | 在网关统一校验 JWT，后端服务信任网关传递的用户上下文 |
| 限流熔断 | 按租户/接口限流，故障时熔断防止雪崩 |
| 协议转换 | 对外 REST，对内可转 gRPC |
| 聚合 | BFF（Backend For Frontend）聚合多个后端为一个接口，减少客户端往返 |

### 2.2 常见网关技术

- Spring Cloud Gateway（Java 生态，响应式）
- Nginx / OpenResty（轻量，四层/七层转发）
- Kong / APISIX（云原生，插件丰富）
- Envoy（Service Mesh 场景）

### 2.3 BFF：一个「非 REST 但正确」的例子

移动端首页往往需要「用户信息 + 推荐列表 + 未读数」——如果让客户端分别调 3 个微服务接口，往返慢且费电。

BFF 模式：为移动端专门提供一个聚合接口（**不是**让微服务互相耦合）：

```
GET /api/mobile/home-summary
→ { "user": {...}, "recommendations": [...], "unread": 5 }
```

这是对 REST「纯资源」原则的合理妥协——**客户端体验优先于教条**。

## 3. REST 的常见坑（避坑指南）

### 3.1 设计坑

| 坑 | 后果 | 正解 |
|----|------|------|
| URL 里写动词 `/getUser` | 风格混乱，无法复用 HTTP 语义 | `/users/{id}` |
| GET 里做删除/写操作 | 预取/爬虫误触发 | 用 DELETE/POST |
| 返回 200 + body 里的错误码 | 客户端要写两套错误处理 | 用真实 HTTP 状态码 |
| 把 DB 主键直接当 API id | 暴露业务规律，且换库即破坏 API | 用全局唯一 ID（雪花/UUID） |
| 列表接口不分页 | 大数据量 OOM / 超时 | 强制分页 + size 上限 |
| 过度嵌套 `/a/1/b/2/c/3/d` | 耦合从属链，难演进 | 扁平化 + 查询参数 |

### 3.2 演进坑

| 坑 | 后果 | 正解 |
|----|------|------|
| 随意删改字段 | 线上客户端崩溃 | 版本管理 + 弃用公告期 |
| 一个接口「顺便」给多个前端用 | 每个需求都动它，回归测试爆炸 | BFF / 分端接口 |
| 无监控 | 不知道接口慢在哪、谁在用 | 网关 + APM（SkyWalking/Prometheus）埋点 QPS、RT、错误率 |

### 3.3 性能坑

| 坑 | 正解 |
|----|------|
| N+1 查询 | 批量加载 / `?include=` 一次取全 |
| 返回全表字段 | 按需 `?fields=id,title`（Sparse Fieldsets） |
| 无缓存 | ETag + Cache-Control + 服务端缓存 |
| 大文件走 JSON | 文件用专门的下载/上传接口（二进制流或对象存储 URL） |

## 4. REST 不是万能：与 GraphQL / gRPC 的分工

| 维度 | REST | GraphQL | gRPC |
|------|------|---------|------|
| 强项 | 简单、缓存友好、生态成熟 | 灵活查询、避免过度获取/不足获取 | 高性能、强类型、内网调用 |
| 弱项 | 字段固定，易过度获取 | 缓存复杂、N+1、学习成本高 | 浏览器原生不支持、可读性差 |
| 典型场景 | 对外开放 API、资源 CRUD | 复杂、多端、数据形状多变 | 微服务间内部调用 |

**成熟团队的常见组合**：

```
对外合作伙伴 / 公开 API  ─── REST（稳定、好缓存、易用）
移动端复杂聚合页        ─── GraphQL 或 BFF
内部微服务间            ─── gRPC（高频、低延迟）
```

它们不互斥。一个系统完全可以「对外 REST、对内 gRPC」。

## 5. 生产级 REST API 完整清单

把 01-04 篇的能力拼起来，一个生产级 REST 服务应具备：

- [x] 资源化 URL，动词走 HTTP 方法（02）
- [x] 版本化（`/v1/`）（02）
- [x] 分页/排序/过滤 + 白名单字段（02）
- [x] DTO/VO 分层，不暴露 Entity（03）
- [x] Bean Validation 参数校验（03）
- [x] 统一错误体 + 全局异常处理，状态码如实（03）
- [x] JWT 无状态鉴权，401/403 语义清晰（04）
- [x] 写接口幂等（Idempotency-Key）（04）
- [x] ETag / Cache-Control 缓存（04）
- [x] 限流（04）
- [x] OpenAPI 自动文档 + 契约评审（04/05）
- [x] MockMvc / 契约测试进 CI（04）
- [x] 网关统一入口、监控埋点（05）
- [x] 接口 Owner 与下线流程（05）

## 6. 面试高频题速查

**基础**
1. REST 是什么？六大约束？—— 见 01。
2. GET/POST/PUT/PATCH/DELETE 语义与幂等性？—— 见 01。
3. 200/201/204/301/304/400/401/403/404/405/409/422/429/500 分别什么时候用？—— 见 02。

**进阶**
4. PUT 和 PATCH 区别？什么时候用哪个？—— 见 02。
5. 如何设计 API 版本管理？三种方案优劣？—— 见 02。
6. 如何做接口幂等？—— Idempotency-Key + Redis，见 04。
7. 401 和 403 的区别？—— 401 未认证，403 已认证无权限，见 04。

**高级**
9. 微服务下 API 网关的作用？—— 见 02/05。
10. REST vs GraphQL vs gRPC 怎么选？—— 见 04/05。
11. 什么是 BFF？为什么它「不纯粹」但正确？—— 见 05。

## 7. 结语：精通的真正含义

精通 REST 不是背下 RFC 和注解，而是能在这些约束之间做**有依据的取舍**：

- 当「无状态」和「用户体验」冲突（BFF 聚合）时，知道为何破例、如何把破例隔离在网关层。
- 当「统一接口」和「性能」冲突（过度获取 vs 多次请求）时，知道何时引入 GraphQL/BFF。
- 当「快速迭代」和「向后兼容」冲突时，知道版本化与弃用流程怎么托底。

指导：**REST 是工具，不是宗教；让系统稳定、好用、可演进，才是目的。**
